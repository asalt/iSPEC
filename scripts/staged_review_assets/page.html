04 / One result, an appropriate role

A tool result is server-provided evidence, not a user instruction or an assistant's claim. The chat template decides how API messages become model-visible text.

Tulu: labeled system message

The cached Tulu template renders system, user and assistant text, but omits native tool messages. iSPEC's system TOOL_RESULT copy keeps the result visible.

<|system|>
TOOL_RESULT ... actual server result ...

OLMo: environment message

The evaluated OLMo template renders API role=tool as environment. Assistant messages carry the model's previous replies and tool calls.

<|im_start|>environment
... actual server result ...<|im_end|>

The current compatibility path sends both API representations; Tulu sees the system copy, while this OLMo template sees both. That is one logical result, not two executions. This viewer does not change that routing. A system label does not grant permission or turn quoted content into policy.

Verified for the cached Tulu and local OLMo evaluation templates, not every model/runtime. Think's adapted template was inspected; no new Think inference was run.

Reading notes

  1. Pass/fail comes from the nearest matching results.xml. Missing or ambiguous results are unknown. Matching comment counts alone are not a pass.
  2. Behavioral findings are separate review annotations. Automatic signals are leads, not semantic verdicts; the response guard can itself be wrong. Unreviewed does not mean correct.
  3. A blocked save is still an attempted save. A delivered correction does not erase a raw false claim. A fixture write does not prove approval or note quality.
  4. These are saved synthetic trials, not new inference or production writes. Repeated cases and changed prompt bundles do not establish causal improvements or deployment readiness.
  5. API request JSON precedes chat-template rendering. Detailed captures can contain private context in other runs; review before sharing.
